# create-canvas 비교 검토 — 가져올 것과 A/B 비교 절차 제안 (2026-10-22)

## 맥락

- 비교 대상: ibelick `create-canvas` 스킬 (https://www.ui-skills.com/skills/ibelick/create-canvas). 여러 컴포넌트를 한 판에 띄워 대화로 비교하고 고치는 스킬이다.
- 우리 쪽: `plugins/hyper-design/core/features/canvas/` (`contract.md` 기준).
- 목적: 목적이 비슷해 보여서 차용할 것이 있는지 본다. 그리고 A/B 비교 검토에 어떤 개념적 절차를 넣어야 결과가 좋아지는지 정리한다.
- 원문은 페이지 요약으로만 읽었다(원문 그대로 받지 못함).

## 1. 같은 점과 다른 점

| | create-canvas | hyper-design 캔버스 |
|---|---|---|
| 판에 올리는 것 | 이미 있는 프로젝트의 실제 컴포넌트 미리보기 | PRD로 새로 만든 화면 HTML(iframe 카드) |
| 판의 축 | 같은 것의 여러 버전을 비교하고 반복 | 서로 다른 화면 사이의 흐름(연결·갈래·정책) |
| 내용 원천 | 소스 안 타입 목록(registry): id·이름·컴포넌트·가짜 데이터·위치·크기 | `screens.json` (`id, file, title, group, purpose, policies, branches`) |
| 고치기 | 대화로 소스 수정. "다른 버전 해 봐"(새 id)와 "이걸 바꿔"(제자리)를 구분 | 편집 메모 → 보내기 → `/hyper-design:fix`. 기본은 제자리 수정 |
| 브라우저 저장소 | 카메라·테마·위치(id 기준)만. 항목을 만들거나 숨기지 못한다. 낡은 id는 무시하고 새 항목은 늘 보인다 | 위치·팔레트·메모·숨김·연결 이름·편집 기록까지 localStorage |
| 이름 | `대상 · 변형` 이름을 누르면 정확히 복사, 성공한 뒤에만 표시 | 카드 제목(`title`) |

겹치는 것은 "여러 개를 한 판에 놓고 본다"까지다. 차용할 가치는 주로 **버전을 다루는 쪽**에 있다.

## 2. 가져올 것 (가치 순)

1. **"다른 버전" ≠ "바꿔".** 지금 fix는 화면 파일을 덮어쓴다. A/B를 하려면 사람이 복사해야 하고, 옛 안은 `.hd-history`에만 남는다.
   - `screens.json` 항목에 `variantOf: "<원본 id>"`, `variant: "<변형 이름>"`을 둔다.
   - "다른 버전"이면 새 id와 새 파일을 만들고 원본 옆 빈자리에 놓는다. 기존 카드는 움직이지 않는다.
   - 캔버스는 같은 `variantOf` 묶음을 형제 카드 한 줄로 그리고, 흐름 선은 원본에만 붙인다.
2. **이름 규칙 `대상 · 변형` + 이름 클릭 복사.** 대화에서 사람과 에이전트가 같은 이름으로 가리킨다. 지금 있는 clipboard 코드(`canvas_template.html`, `navigator.clipboard.writeText`)를 다시 쓴다.
3. **저장소에 담는 것을 계약으로 고정.** 숨김 목록(`HKEY`)이 다시 만든 뒤에 새 화면을 가릴 여지가 있고, 버전이 생기면 id가 늘어 위험이 커진다.
   - 숨김 목록에 없는 새 id는 늘 보인다. 저장 문서에 버전 번호를 붙인다. `contract.md`에 한 줄로 적는다.
4. **최종 보고 형식.** 바뀐 경로, 새로 생긴 미리보기 이름, 돌린 검사, 검사하지 않은 것, **묻지 않고 고른 기본값**. 마지막 항목은 지금 보고에 없다.
5. **가져올 필요 없음.** 카메라(이동·확대·맞추기), 모듈 분리, 테스트 층, 접근성은 우리 쪽이 이미 더 깊다.

## 3. A/B 비교 검토 절차 제안

나란히 놓기만 하면 "보기 좋은 쪽" 고르기로 끝난다. 아래 순서를 넣는다.

1. **가설을 먼저, 변형은 축 하나만.** 변형마다 "무엇을 바꿔 무엇이 나아질 것"을 한 줄로 쓴다(예: `B: CTA를 위로 → 첫 행동까지 시간 단축`). 축 두 개가 같이 바뀌면 원인을 알 수 없다. 이 줄은 카드 `purpose`에 둔다.
2. **기준을 비교 전에 고정.** PRD 목표, `conventions.json` 관례, 접근성에서 3~4개를 미리 고르고 그 위에서 채점한다. 보고 나서 정한 기준은 마음에 드는 쪽에 맞춰진다.
3. **같은 조건에서 보기.** 같은 데이터·팔레트·크기로 보고, 빈 상태와 오류 상태도 함께 본다. 팔레트 전환과 max 상태 화면이 있으니 **변형마다 상태 행렬**을 보는 것이 우리 강점이 된다.
4. **이름을 가리고 판정.** 만든 에이전트는 자기 안을 편드는 경향이 있다. A/B 이름과 순서를 섞어 별도 판정자에게 넘기고, 기준별 근거를 적게 한다.
5. **결정을 남기고 진 쪽에서 가져오기.** "B 채택, A의 요약 카드는 가져옴"처럼 합치기를 기본 결과로 둔다. 결정과 이유는 `decisions.json`에 남긴다. 진 안은 지우지 않고 `rejected`로 표시해 캔버스에서 접는다. 같은 실험을 되풀이하지 않게 된다.

흐름: **가설 → 고정 기준 → 같은 조건 → 가린 판정 → 기록·합치기.**
