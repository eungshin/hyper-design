# 캔버스 개선 요청 — 실사용 추적에서 나온 것

캔버스를 고치는 세션(/re 트랙 `canvas-edit`)이 읽는 목록. **캔버스 시스템 사항만** — 제품 내용은 적지 않는다(규칙: `README.md`). 근거는 각 세션 폴더의 `log.md` 마찰 표(F 코드)와 `rounds.jsonl`.
이미 백로그에 같은 항목이 있으면 새 일을 만들지 않고 그 번호에 근거만 더한다.

## R1. 보낸 메모에 "반영됨" 표시 (2026-10-23, Master 요청)

- **요청:** 보낸 메모 중 실제로 구현된 것은 캔버스에서 한눈에 "구현 완료"로 보여야 한다. 지금은 보낸 뒤 반영됐는지 사람이 화면을 하나씩 열어 비교해야 한다.
- **백로그:** canvas-edit #231(`hd reply --kind 반영됨|답변|질문|보류` + 메모 목록 상태 칩 + 패널 거르기)이 같은 것. #228(상태 파일)의 메모 상태 `작성 중 → 보냄 → 반영됨`이 그 바탕.
- **이번 실사용에서 더해진 조건:**
  1. **부분 반영**이 있다. 한 메모 안 요청 둘 중 하나만 된 경우(로그인: 이메일 칸 done, 가운데 정렬은 그 뒤에)가 10건 중 3건. `반영됨`과 `보류` 사이에 "일부 — 남은 것 한 줄"이 필요하다.
  2. **보류는 이유와 함께 그 자리에서** 보여야 한다. AI가 예시 사전 제거를 "다음 조각"으로 미루고 끝 보고에만 적었더니, 사람은 미반영으로 읽고 다시 지적했다(F12). 보류 칩 + 이유 한 줄이 있었으면 왕복 하나가 없었다.
  3. **결정으로 바뀐 메모**(다른 화면에 합침, 거절)도 상태가 필요하다. 질문창 빈 레이아웃은 "기존 화면에 합침"으로 결정됐지만 카드엔 아무 표시가 없어 사람이 "왜 아직 비었나"를 물었다(F13). → `답변`이나 `보류`가 아니라 "대체됨 — 어디로" 한 줄.
  4. 반영 표시는 AI가 화면 파일을 고친 뒤에 붙인다. 붙인 근거(고친 화면 id, 캡처 확인 여부)를 칩 툴팁에 남기면 사람이 믿고 넘어간다.
- **근거:** `2026-10-23-dayfine-onboarding/log.md` F1·F2·F12·F13, `rounds.jsonl` round 4 item 1·7·8·9·10.

## R2. 빈 레이아웃은 만들 때 화면 파일로 (F13)

- 빈 레이아웃 카드는 브라우저에만 있고 `screens.json`·`screens/` 에 없다. AI가 채우려면 화면을 새로 만들어 등록해야 한다. #228 상태 파일에 실리면 AI가 적어도 읽을 수는 있다 — 그 단계에서 빈 레이아웃의 이름·목적이 상태 파일에 들어가는지 확인.

## R3. PRD → spec 인용 연쇄 (F10)

- PRD를 고치면 `spec_inventory.json` quote가 낡아 selfcheck가 막는다. PRD 갱신과 quote 갱신이 한 명령이면 손 수정이 없어진다. 캔버스 범위 밖(하네스 `scripts/`)일 수 있음 — 판단은 그 세션이.

## R4. 전달이 받는 세션에 닿지 않음 (2026-10-23, F1·F2)

- "전달"은 `.hd-queue/` 파일에만 쌓이고 받는 세션이 없으면(`__hdAgent=null`) 아무도 모른다. 메모 원본은 브라우저 localStorage에만 있어 AI는 붙여 넣은 것만 읽는다. 1~3차 6건이 반영 없이 쌓였고 사람이 같은 요청을 다시 보냈다.
- **백로그:** #228(상태 파일) · #229(hd notes) · #230(hd wait/attach). 더할 조건: 받는 세션이 없을 때 캔버스가 "받는 곳 없음 — 대기열에만 저장됨"을 보여 줘야 한다(사람이 보냈다고 믿지 않게).

## R5. 빈 레이아웃 전달에 메모 본문이 빠짐 (2026-10-23, F3)

- 빈 레이아웃을 보내면 "메모대로 채우기"라는 껍데기 항목만 가고, 그 화면에 남긴 메모 본문은 별도 항목으로 나가거나 빠진다(2차: 본문 없음, 4차: item 9 껍데기 + item 10 본문). 빈 레이아웃 요청 하나에 목적·메모 본문이 함께 실려야 한다.

## R6. 같은 요청이 여러 요소로 갈라져 나감 (2026-10-23, F6)

- 사람이 같은 문장을 인접한 두 요소에 달면 두 항목으로 나간다(4차 item 7·8). 보내기 직전 같은 화면·같은 글의 메모를 하나로 묶거나 "같은 요청 2곳"으로 표시.

## R7. 메모 범위가 화면 하나로 고정됨 (2026-10-23, F8)

- "모든 화면에 동일하게"(움직이는 그라데이션) 같은 요청도 화면 하나(login)에 붙어 나가 AI가 범위를 추측해야 했다. 메모에 범위 선택(이 요소 / 이 화면 / 전체)이 필요하다.

## R8. fix 작업자 규칙과 요청 종류의 불일치 (2026-10-23, F9)

- screen-reviser는 "COMPONENTS 클래스만" 규칙이라 새 부품(가운데 정렬, 구분선, 스크롤 목록)이 필요한 요청 3건 중 2건이 partial·not found로 돌아왔다. 규칙은 옳게 막았다. 필요한 것: fix 1단계에서 요청을 "있는 부품으로 됨 / 새 부품 필요"로 갈라, 새 부품 쪽은 처음부터 메인(또는 부품 작업자)에게 보낸다.

## R9. 공용 CSS 수정의 부작용을 selfcheck가 모름 (2026-10-23, F11)

- `components.css`의 `.auth` 한 줄이 다른 화면(login--done) 배치를 깨뜨렸고, 렌더 캡처로만 발견했다. fix 4단계 확인에 "바뀐 클래스를 쓰는 모든 화면 캡처"가 들어가야 한다.

## R2 니즈 확정 (2026-10-23, Master)

- **원하는 동작:** 빈 레이아웃에 남긴 요청대로 AI가 화면을 만들면, 캔버스가 **빈 카드를 지우고 그 자리를 생성된 화면으로 채운다.** 사람이 빈 카드를 손으로 지우거나 새 카드를 찾아 옮기지 않는다.
- **조건:** 빈 카드의 위치·연결선·폴더·메모를 새 화면이 그대로 이어받는다. 바뀐 뒤 메모는 R1의 상태 표시(반영됨, 근거: 새 화면 id)로 닫힌다. 되돌리기 한 번으로 빈 카드로 돌아갈 수 있어야 한다.
- **지금:** 새 화면이 따로 생기고 빈 카드는 남는다(round 5: `guide-query` + 빈 카드 `new-i2tiypq`).

## R10. 실사용 빌드가 개발 중인 캔버스 코드에 묶임 (2026-10-23, F14)

- 실사용 결과 폴더를 빌드할 때 `build_canvas.py`가 작업 트리의 템플릿·모듈을 읽는다. 캔버스를 고치는 세션이 미커밋 상태(새 모듈 참조만 있고 파일 없음)면 실사용 빌드가 `AssertionError: 캔버스 모듈이 없다`로 멈춘다. 이번엔 `git archive HEAD`로 꺼낸 사본으로 빌드해 우회했다.
- 필요한 것: 실사용은 커밋된(또는 고정된) 캔버스 판으로 빌드하는 길 — 예: `build_canvas.py --from-ref HEAD`, 또는 하네스를 설치본(plugin 캐시)에서 돌리기. 개발 세션과 실사용 세션이 같은 폴더를 쓰는 동안은 계속 생긴다.

## R2 보강 (2026-10-23, round 5)

- 같은 일이 다시 생겼다: 사람이 빈 레이아웃을 질문창 안내로 채워 달라고 했지만 AI는 그 카드를 채울 수 없어 새 화면(`guide-query`)을 따로 만들었다. 이제 캔버스에 빈 카드와 새 화면이 둘 다 있고, 빈 카드는 사람이 지워야 한다. 빈 레이아웃 → 화면 파일로 "승격"하는 길이 있어야 같은 자리에서 채워진다.

## R10 보강 (2026-10-24)

- 다시 생겼다: 다음 날 서버를 다시 띄울 때도 작업 트리가 미커밋(annotation·view-notes 등)이라 HEAD 사본(`git archive HEAD` → Temp)으로 빌드하고 그 사본의 `helper.py`로 띄웠다. 실사용 세션이 매번 이 우회를 손으로 한다.
- 함께 생긴 것: helper를 다시 띄우면 `?hd=` 토큰이 바뀌어 사람이 들고 있던 주소가 죽는다. 같은 out을 다시 열면 주소가 같거나, 옛 주소가 새 주소로 넘어가야 한다.
- 같은 날 또 생겼다: 내가 띄운 helper가 몇 분 뒤 exit 1로 죽었고, 그 사이 다른 프로세스(pid 7308, 누가 띄웠는지 확인 못 함)가 같은 out·같은 포트 12279로 새 토큰을 받아 떠 있었다. 사람에게 알려 준 주소가 다시 죽었다. 한 out에 helper 하나만(이미 떠 있으면 그 주소를 돌려주기)이어야 한다.

## R11. 화면 템플릿의 칸 배치가 '뒤로' 링크 유무에 흔들림 (2026-10-24, F16)

- `.wizard-main`이 `auto / 1fr / auto` 세 줄인데, 뒤로 링크가 없는 화면은 내용이 첫 줄(auto)에, 바닥 줄이 가운데(1fr)에 들어가 내용이 위로 붙었다. 결과 폴더의 components.css에 `.wizard-content{grid-row:2}` `.wizard-foot{grid-row:3}`를 더해 고쳤다. 표면 `desktop-wizard`의 부품 원본(하네스 쪽)에 같은 고정이 들어가야 다음 실행에서 다시 생기지 않는다.


## R12. 앱 무대(twin) 카드 로딩·데이터 (2026-10-24, #222)

- 상세 측정과 후보: `2026-10-23-dayfine-onboarding/twin-loading.md`.
- 요약: 서버 시작 20초 + 첫 무대 13초(요청 197개), 데운 뒤 1.3초. 설정 탭 무대가 언제나 `usage-tab` 스냅샷으로 채워져 사전 탭이 빈(모순된) 화면이 된다. 카드 크기 520×640은 설정 창에 좁다. 서버가 꺼지면 대체 표시가 없다. 정적 화면 안에 무대를 끼우는 모양(설명 + 실제 부품)이 실사용에서 바로 필요했다.
- 우선순위 제안: 1) 탭별 fixture 2) 예열 3) 무대별 크기 4) 꺼짐 표시 5) 중첩 지원 여부 결정.

## R13. 바깥에서 컴파일한 앱 목업을 화면으로 올릴 길이 없음 (2026-10-24, round 7)

- 사람이 앱 부품 목업(팝업 탭 줄, 설정 사전 목록)을 캔버스에서 보고 메모하길 원했다. 앱 쪽 목업 체계(dictionary `src/mockup`, 실제 Svelte 부품을 한 파일로 컴파일)가 만든 7MB 단일 HTML을 `screens/`에 복사해 `screens.json`에 손으로 등록했다.
- 마찰: 1) selfcheck가 캔버스용 화면 규칙(배지 표, 이모지, 인라인 style, 색 하드코딩, h1 개수, tokens 링크, 깨진 참조)을 컴파일된 앱 번들에 그대로 적용해 화면마다 약 10건이 실패했다. 2) `palette.js`가 없으면 고르기·메모를 할 수 없어 `</body>` 앞에 손으로 넣었다. 3) 카드 1080×680에 세로로 긴 목업 페이지가 들어가 판 위에서는 첫 화면만 보인다.
- 필요: `kind: "external"`(또는 `source: app-mockup`) 화면 — selfcheck는 링크·메모만 검사, palette.js는 빌드가 넣어 주고, 카드 높이는 문서 높이를 따르거나 스크롤 표시. 앱 목업 빌드 → 화면 등록을 한 명령으로.
